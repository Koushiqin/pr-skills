# 面试话术样例库

本文件是 ProjDebrief 的话术风格基准。每次出话术前先对照本文件；样例 ≥3 条后，新话术必须与样例口吻一致。

## 维护方式

- 用户把已有话术贴在对话里并说"加到样例库"时，按下方固定格式整理后追加到本文件末尾
- 可以归一化格式，但**不改写话术原文内容**（保持用户口吻，这是样例库的价值）
- 用户也可直接编辑本文件

## 条目格式

```markdown

- 追问与应答：<被追问时怎么接>
```

## Q: 你项目里怎么做熔断降级的？

- 考察点：容错设计 / 微服务稳定性。面试官想看你有没有考虑过下游挂了怎么办，而不是接口调不通就直接报错给用户。
- 项目落点：`service/order/src/main/java/.../OrderService.java` 行 128–156（调用 InventoryClient 的地方），`config/FallbackConfig.java` 行 45–62（兜底逻辑）
- 人话版：下单的时候要调库存服务扣库存，但库存服务要是挂了或者超时，不能让下单接口跟着崩。我们加了一层保护——连续调用失败 5 次之后，接下来 10 秒内就不真调了，直接走一个兜底逻辑返回"稍后重试"。等库存服务恢复了再自动切回去。
- 话术版："我们在订单服务调库存扣减那一段加了熔断保护。具体是这样的：用了框架的熔断组件，配置的是连续失败 5 次就打开，半开状态放一个请求进去探活，成功了就恢复，失败就继续熔断。兜底逻辑就是返回一个'库存服务暂时不可用，请稍后重试'的友好提示，而不是直接抛异常给用户。当时踩过一个坑——刚上线时熔断阈值设太低，下游偶发抖动就被熔断了，后来调成看 P99 超时率而不是单次失败，稳定多了。"
- 追问与应答：
  - 追问：用的哪个熔断框架？→ 应答："用的 Resilience4j，因为我们项目已经引了 Spring Cloud，它是官方推荐的，和配置中心集成也好做。之前考虑过 Sentinel 但那套主要是流量控制，我们这里主要是下游容错，Resilience4j 更轻量。"
  - 追问：怎么知道下游恢复了？→ 应答："半开状态会放一个探测请求进去，成功了就把熔断计数清零重新开始；探测失败就再等 10 秒再试。这个窗口时间是在配置里调的，不用改代码。"
  - 追问：有没有降级策略？→ 应答："熔断是第一步，降级是在兜底那层做的——库存扣减熔断时返回友好提示；如果是积分服务挂了，降级策略是本次下单不记积分，等服务恢复后异步补记，这个是在 FallbackConfig 里配的，不同下游可以有不同降级。"

## Q: XxxService 里这个 @Async 注解加在这里是干嘛的？

- 考察点：异步执行 / 性能优化（不是标准面试提问，是用户的不解）
- 项目落点：`service/xxx/src/main/java/.../XxxService.java` 行 203（`@Async public void sendNotification(...)`），`config/AsyncConfig.java` 行 18–35（线程池配置）
- 人话版：这个方法是发通知用的——下单成功后要给用户推一条站内信。原来直接在主线程里调，发通知的 RPC 慢的时候会拖慢整个下单接口的响应时间。加了 @Async 之后，这个方法会被扔到一个单独的线程池里跑，主线程不等它，下单接口可以立刻返回。
- 话术版：（轻量模式，不输出）
- 追问与应答：
  - 追问：那如果通知发失败了怎么办？→ 应答："这个是异步的，失败不会影响主流程。我们在异步方法里加了 try-catch，失败会记日志，然后有个定时任务扫失败日志重发。如果重发三次还是失败，就留着等人工介入。"

## Q: 盘一下这个项目的权限校验是怎么做的？

- 考察点：认证鉴权 / 安全设计 / AOP 应用。面试官想知道你有没有考虑过"谁能调这个接口"，以及是在每个接口里硬写还是统一处理。
- 项目落点：`common/security/src/main/java/.../AuthInterceptor.java` 行 32–78（拦截器主体），`controller/` 下各接口的 `@RequireRole` 注解，`config/WebMvcConfig.java` 行 55（注册拦截器）
- 人话版：每个请求进来先过一层拦截器，从 token 里解析出用户信息，查一下这个用户有没有当前接口要求的角色。有就放行，没有就返回 403。接口上用注解标一下需要什么角色，不用每个接口里手写权限判断。
- 话术版："我们把权限校验统一做在一个 Spring MVC 拦截器里。流程是这样的：请求进来先被 AuthInterceptor 拦截，从请求头拿 token 解析出 userId 和角色列表，然后看当前接口有没有标 @RequireRole 注解——如果标了就比对用户角色，没有匹配的就返回 403。token 校验和角色比对都是在拦截器里统一做的，接口代码只写业务逻辑，不用操心权限。踩过一个坑是拦截器把登录接口也拦截了，导致登录请求拿不到 token 直接 403，后来在拦截器里加了白名单配置。"
- 追问与应答：
  - 追问：token 存在哪？→ 应答："用户登录成功后服务端生成 token 返回给前端，前端每次请求放在 header 里。token 里存的是 userId 和角色，用 JWT 签名，服务端不需要存 session，无状态的。"
  - 追问：怎么防止 token 被篡改？→ 应答："用了非对称加密的签名，拦截器里验签，改了任何字段签名都会过不了，直接返回 401。token 还有过期时间，默认 2 小时，过期要重新登录。"
  - 追问：如果要加一个新的角色，改哪里？→ 应答："角色是在用户表里存的，前端管理后台可以给用户分配角色。接口上加 @RequireRole("新角色名") 就行，拦截器的逻辑是通用的，不用改。不过角色的枚举我们在 constants 里有个常量类统一管理，避免字符串写错。"
