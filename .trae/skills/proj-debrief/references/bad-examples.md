# 坏味反例库

使用说明：遇到新的坏输出案例就追加到这里，持续积累。
格式：坏输出长什么样 → 为什么不好 → 正确写法应该是什么样。

---

## 反例 1：无代码证据编造设计模式

### 坏输出长什么样
"我们项目里用了观察者模式来做订单状态变更的通知——下单成功后触发一个事件，所有订阅了这个事件的服务都会收到通知，比如库存扣减、积分发放、短信推送。"

### 为什么不好
项目里根本没有观察者模式的实现（没有 Event、没有 Listener 接口、没有事件发布代码）。实际是在 OrderService 里直接串行调用 inventoryClient.deductStock()、pointsService.addPoints()、smsService.send()。编造设计模式等于把面试话术建立在虚假事实之上，面试官一追问"事件在哪里发布的？Listener 有几个？"就会崩。

### 正确写法应该是什么样
先在代码里找证据。找到 OrderService.java 行 130-135 是三个服务的串行调用，就如实写："下单成功后我们在 OrderService 里顺序调了三个下游——库存扣减、积分发放、短信推送。现在是同步串行的，后面考虑改成异步解耦。"不要加不存在的观察者模式。

## 反例 2：编无数据支撑的量化结论

### 坏输出长什么样
"我们用了 Spring 自动装配之后，启动速度提升了 40%，代码量减少了 30%。"

### 为什么不好
- 40% 和 30% 这两个数字从哪来的？项目里没有任何性能测试报告或 benchmark 数据支撑。
- 面试官能继续追问"怎么测的？基线是多少？"，答不上来就扣分。
- style-guide.md 明确把"大幅提升/性能提升 X%"列为禁用表达。

### 正确写法应该是什么样
有数据就说数据来源，没数据就说事实不说比例："用了自动装配之后，原来每个模块要写的 XML 配置文件基本都删掉了，启动时少了不少手动扫描的步骤。"只陈述能自证的事实，不编百分比。

## 反例 3：先甩术语再解释（违反解释顺序）

### 坏输出长什么样
"这个用了观察者模式。观察者模式是一种行为设计模式，它定义了一对多的依赖关系，当一个对象状态变化时，所有依赖它的对象都会收到通知并自动更新。"

### 为什么不好
style-guide.md 硬规则："做什么 → 为什么 → 术语"。先抛术语再倒过来解释是什么、再说为什么要用，面试官会觉得你在背八股而不是在讲自己项目的实现。正确的顺序应该是"先讲我们要解决什么问题 → 我们怎么解决的 → 这个做法的正式名词是什么"。

### 正确写法应该是什么样
"我们当时遇到一个问题——订单状态变了之后，库存、积分、短信好几个地方都要同步更新。如果每个地方都去查订单状态变化，代码会很散。所以我们做了一个事件机制：订单状态改的时候发一个事件，谁关心谁订阅。这个做法有个正式名词叫观察者模式，就是一个对象变了通知一批依赖它的对象。"

## 反例 4：话术风格和样例库差太远（书面腔、堆形容词）

### 坏输出长什么样
"综上所述，我们的微服务架构在容错设计方面展现了卓越的工程实践能力。值得一提的是，通过引入 Resilience4j 熔断框架，我们构建了一套完整的弹性防护体系，显著提升了系统在面对下游服务异常时的鲁棒性与稳定性。"

### 为什么不好
- "综上所述/值得一提的是"是 style-guide.md 禁用的书面腔
- "卓越的工程实践能力/完整的弹性防护体系/鲁棒性与稳定性"都是堆出来的形容词，面试现场说出来很假
- 和 talk-track-examples.md 里的口语风格（"用了框架的熔断组件""踩过一个坑""调成看 P99 超时率"）完全不搭

### 正确写法应该是什么样
"我们在订单服务调库存那一段加了熔断保护。用的是 Resilience4j，配的连续失败 5 次就打开，半开探活恢复。兜底就是返回'稍后重试'，不抛异常。刚上线时阈值设太低，后来调成看 P99 超时率就稳定了。"

## 反例 5：用户说法错误时帮圆（违反冲突协议）

### 坏输出长什么样
用户问："你们用的是 Dubbo 对吧？"但项目实际用的是 Spring Cloud OpenFeign。
输出："对，我们项目里有 Dubbo 的部分……"（然后硬编一段 Dubbo 的使用方式）

### 为什么不好
节 8 冲突协议明确说"不为了顺应用户而两边都说对"。帮圆等于把错误事实固化成面试话术，用户拿去面试时如果被追问 Dubbo 细节，必死无疑。正确行为是停下来标注不一致，等用户确认。

### 正确写法应该是什么样
```
⚠ 与项目实现不一致
你的说法：我们用的是 Dubbo
代码事实：service/order/.../OrderService.java 行 45 用的是 @FeignClient，整个项目依赖里也只有 spring-cloud-starter-openfeign（pom.xml 行 128-135）
差异点：Dubbo 是另一套 RPC 框架，我们项目用的是 Spring Cloud OpenFeign
先停在这里——是你记错了，还是项目里另有 Dubbo 的实现需要我找一下？
```

## 反例 6：跨项目引用记忆

### 坏输出长什么样
用户项目是 Python Flask 写的，但模型输出："这个和我之前做的那个 Spring Boot 项目里的 XxxService 一样，都是用了 @Async 异步化。"

### 为什么不好
节 4 明确禁止跨项目串事实。用户只关心"他的项目里是怎么做的"，引用别的项目的实现细节不仅跑题，还可能让用户误以为那个实现也存在于他的项目里。

### 正确写法应该是什么样
只谈当前项目的代码："这个 Flask 路由里用了后台线程做通知发送——看 app/routes/order.py 行 78，new Order 成功后用 threading.Thread 起了一个后台任务发邮件，不阻塞主响应。"
